# 设计笔记（面试答辩提纲）

这份文档是给"被追问"准备的：每个决策写清楚**当时的选项**和**为什么选它**，
以及**它现在的弱点在哪**。面试里最容易被记住的不是"我做了什么"，
而是"我知道它在什么情况下会坏"。

## 一句话

Mend 是一个把「测试从红变绿」当作唯一完成标准的代码修复 agent。

## 目标 / 非目标

**目标**

- 在真实仓库里做小改动（修一个 bug、补一个边界处理），改动可 review
- 每一步可解释、可回放：读了什么、改了什么、测试输出是什么
- 没有密钥也能复现整条流水线（离线假模型 + 自带评测任务）
- 有指标：通过率 / 步数 / 耗时

**非目标**

- 不做多智能体协作、不做 IDE 插件、不做通用编程助手
- 不追 SWE-bench 全量分数（不如自己造 10 个能讲清楚的小任务）
- 不做跨文件大重构（见「已知弱点」）

## ADR-1 完成标准是「测试通过」，不是「模型说完成了」

**选项**：A. 模型输出总结即结束；B. 只有测试通过才算结束。

**选择 B**，并且把判断做进循环里：只要 agent 有写权限，任何「我做完了」的声明
都要过验证门；测试失败就把报错原文回灌，继续改。

**代价**：会多跑测试（评测里一个任务能跑 3 次 pytest）；如果用户的测试本来就慢，
每一步都要等很久。

**下一步**：按 diff 指纹缓存验证结果——代码没变就不重复跑。

## ADR-2 权限靠结构，不靠提示词

**选项**：A. 在系统提示词里写"plan 模式下不要修改文件"；B. 工具分级挂载。

**选择 B**。`plan` / `review` 只挂 read 级工具：写工具的 schema 根本不给模型，
就算模型幻觉出一个 `edit_file` 调用，`registry.call()` 也会因为"没有挂载"而拒绝。
提示词是一种请求，结构才是一种保证。

## ADR-3 零依赖核心 + 可替换的 LLM 适配层

**选项**：A. 用 LangChain / LlamaIndex；B. 用 httpx + typer + pydantic；C. 只用标准库。

**选择 C**。`urllib` 调 API、`argparse` 做 CLI、`tomllib` 读配置。
好处是 `git clone` 之后不用建虚拟环境就能跑，面试官复现成本接近零，
而且每一行循环逻辑都是自己的，讲得清。

**代价**：没有异步、没有重试、没有 provider 抽象层。要换 Claude 的原生
tool-use 协议时，得在 `llm.py` 里加一个实现（接口已经留好了）。

## ADR-4 轨迹 first

每一步都落盘成 jsonl（`.mend/runs/<run-id>.jsonl`），包括工具参数、耗时、
测试输出尾巴。理由很实际：agent 出错时，你唯一能依据的就是"它当时看到了什么"。
`mend trace <id>` 可以直接回放，面试时当场放一段轨迹比讲架构更有说服力。

轨迹的第一行是 run 头（任务 / 仓库 / 起始时间），所以运行列表不用打开文件就能显示任务。
每个步骤带 `at_ms`（相对开始的偏移），这样记录读起来是"第几秒发生了什么"，而不是一串孤立的耗时。

## ADR-5 输出层自己写，不引 rich

**选项**：A. rich / colorama；B. 自己写 ANSI。

**选择 B**。颜色只在 TTY 下输出（`sys.stdout.isatty()`），并且尊重 `NO_COLOR` /
`FORCE_COLOR` 这两个通行约定，再加一个 `--color always|never` 方便在 CI 里强制。
一共 200 行不到，却保住了"零依赖"这个卖点（ADR-3）。

**颜色只用来区分信息等级**：成功绿、失败红、元信息灰、工具名按权限级别上色
（read 蓝 / write 黄 / shell 紫）。装饰性的配色一律不做——终端里最多的是文字，
颜色一多就没法一眼扫出"哪一步失败了"。

还有一个容易忽略的细节：报告里的 diff 只包含**这次运行改过的文件**
（`registry.touched` 收集写入过的路径，再 `git diff HEAD -- <paths>`），
否则工作区里你自己手改的东西会被算成 agent 的产出。

## ADR-6 测试文件不可写：把道德风险变成结构问题

**选项**：A. 提示词里禁止改测试；B. 工具层直接拒绝写测试文件。

**选择 B**（提示词也留着，但不当保证用）。`protected_paths` 里的路径，
写工具在 `registry.call()` 就返回拒绝，而且被拒绝的尝试也会写进轨迹——
"它试图改测试文件"和"它改成功了"一样值得被 review。

**刻意留下的缺口**：配置文件（`pytest.ini` / `pyproject.toml`）不在默认保护列表里。
理由是 agent 经常需要合法地改它们（加依赖、改打包配置），一刀切会挡住正常活；
代价是理论上它可以用 `--ignore` 这类手段绕开验证。这是取舍，不是疏忽——
真想收紧就往 `protected_paths` 里加。

## ADR-7 命令执行：三层纵深防御，而且我知道它不是沙箱

能跑任意命令的 agent 是危险的，所以叠了三层：

1. **命令白名单**：只放测试和 linter 这类工具（`pytest` / `npm` / `cargo` / `ruff` / `ls` …）。
2. **路径检查**：白名单只管第一段命令名，`python -c "open('.env').read()"` 能绕开
   文件工具的路径限制，所以命令串里出现禁止路径就直接拒。匹配时要求两侧是分隔符，
   免得把 `os.environ` 里的 ".env" 误判成路径。
3. **子进程环境里不含 API key**：不是靠字符串匹配挡住读取，而是根本不传给它。

**这不是沙箱。** 白名单里的 `python` 本身就能做任意文件操作，路径检查也只是字符串
层面的拦截（有心绕是绕得过去的）。真正的隔离要把命令放进容器里跑——列在 Roadmap 里。
面试时这一点要主动说：把"我知道它在什么情况下会坏"讲清楚，比声称"我做了安全隔离"可信。

## 被测试和真实模型抓到的三个设计错误（真实踩坑记录）

1. **模型什么都没改就说"我改好了"，循环直接结束了。**
   最初的判断是"只有改过文件才需要验证"，于是"没改任何东西却说修好了"这种最该
   被拦下的情况反而漏过去了。改成：只要有写权限，任何完成声明都过验证门。

2. **"同样的失败"永远检测不出来。**
   防打转靠比较前后两次失败的输出，但工具输出头部带了耗时（`exit=1 (123ms)`），
   每次都不一样，导致指纹永不相等。改成先抹掉带时间的头部和时长数字，再取末尾
   做指纹（见 `agent.failure_signature`）。

3. **离线剧本和坏仓库放在同一个目录，真实模型会读到答案。**
   评测任务自带一份"离线剧本"（不接模型时回放用）。一开始它和坏仓库放在一起，
   而评测会把 fixture 整个复制成任务工作区——于是答案就留在了考场上。
   第一次接真实模型跑评测，轨迹第一行就出现了 `read_file ... fake_script.json`，
   而那个文件里写着正确的 old/new 两段文本。现在剧本挪到 `evals/scripts/`，
   和任务定义放在一起，工作区里只有坏仓库本身。
   **这条只有真的接上模型跑一次才会暴露**：离线模式下"模型"本来就在读剧本，
   从输出上完全看不出异常——评测本身失效了，而报告依然全绿。

前两条是先写测试才发现的，第三条是接上真实模型才发现的。如果只手动跑一遍 happy path，
三个 bug 会一直躺在代码里。

## 已知弱点（面试官大概率会问）

| 弱点 | 现状 | 计划 |
|---|---|---|
| 配置文件不受保护 | `pytest.ini` / `pyproject.toml` 能改（agent 常需要合法地改它们） | 想收紧就加进 `protected_paths`，见 ADR-6 |
| 命令执行不是沙箱 | 白名单 + 路径检查 + 不传密钥，三层都只是"拦截" | 把命令放进容器，见 Roadmap |
| 上下文选择是关键词打分 | 中文用 2-gram 兜底，大仓库会退化 | tree-sitter 做符号索引 |
| 只能改单文件 | `edit_file` 是唯一匹配替换 | 多文件 patch + 事务性回滚 |
| 验证会重复跑测试 | 实测一次 4 步的 run 里 pytest 跑了 3 次（模型自己 1 次 + 验证门 1 次 + 评测判定 1 次） | 判定必须独立跑，所以刻意保留；能省的是让模型自己少跑一次 |
| 没有并发和成本控制 | 单线程；只统计 token | 并发评测 + 预算上限 |
| 只在 Python 项目上真跑过 | 测试命令探测已支持 npm / go / cargo | 补 Go / TS 的评测任务 |

## 失败模式清单

- **改测试来让测试变绿** -> 结构约束：写工具拒绝测试文件（`protected_paths`），被拒的尝试留在轨迹里
- **原地打转** -> 失败指纹去重 + "换思路"提示；连续三次同样的失败直接 `stuck` 停下交给人
- **测试本身写错了** -> 模型会在报告里说明理由（实测过），坚持改代码的会在 `stuck` 处停下
- **命令跑飞** -> 白名单 + 路径检查 + 超时 + 非 shell 调用（不做字符串拼接）
- **改错位置** -> `edit_file` 要求唯一匹配，宁可报错让模型重读文件
- **参数名幻觉** -> 按 schema 校验参数，把错误原文回灌给模型
- **上下文爆炸** -> 先地图后文件，读文件限 400 行，超大文件不参与关键词扫描
- **越界/泄密** -> 文件工具：路径必须落在仓库内、`forbidden_paths` 禁读禁写；命令：见 ADR-7

## 评测口径

- 一个任务 = 坏仓库 fixture + 一句任务描述 + 一条判定命令
- 判定命令通过 = 任务通过（不看模型怎么描述自己）
- 记录：是否通过 / 步数 / 耗时（`mend eval --json` 可导出）
- 评测在临时目录里跑，fixture 会先 `git init` 出一个基线提交

**下一步**：加难度分层（单行 bug / 跨文件 / 需要加测试），并统计"步数 vs 成功率"
来判断是模型能力不够还是循环设计有问题。

## 下一步

1. 多文件 patch + 失败自动回滚（现在的 `edit_file` 一次只能改一处）
2. 用 tree-sitter 做符号索引，替代关键词初筛
3. 评测集扩到 10+ 任务，加难度分层（单行 bug / 跨文件 / 需要加测试），出成功率曲线
4. 命令放进容器里跑，把三层拦截换成真隔离

## 考虑过但没做（以及为什么）

- **按 diff 指纹缓存验证结果**：本来在 Roadmap 里，算了一下只有"评测判定"那一次能命中，
  而**判定必须独立跑**（不能拿 agent 自己的结论当判定结果），验证门重复触发的概率又很低。
  为了省一次 pytest 而引入"可能复用旧结论"的错误面，不值得，所以删了。
- **用 LLM 摘要压缩上下文**：先做符号索引更实在——关键词初筛的瓶颈在"选错文件"，
  不在"描述太长"。
- **专门集成 formatter / linter**：`run_command` 已经能跑 `ruff`，再包一层只是重复造轮子。
